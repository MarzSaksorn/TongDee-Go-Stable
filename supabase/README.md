# Supabase schema management

This directory makes the Thong Dee Go database schema reproducible. The live project is `jbafdzoihklmfurywmhs` (see `.env.example`).

## Layout

- `migrations/` — versioned SQL migrations (the source of truth)
  - `20260816000000_init.sql` — baseline snapshot of the live schema captured 2026-08-16 (20 tables, RLS policies, functions, triggers)
- `legacy/` — outdated pre-migration SQL files (schema.sql + seed files). Superseded by `migrations/`; kept for reference only. The seed data in `src/data.ts` is the current source of seed content.
- `config.toml` — generated by `supabase init`

## Workflow

Prerequisite: Supabase CLI (run via `npx supabase` if not on PATH).

```bash
# One-time: link to the remote project (asks for the DB password)
npx supabase link --project-ref jbafdzoihklmfurywmhs

# Apply migrations to the remote
npx supabase db push

# Capture drift from the remote back into a new migration
npx supabase db pull
```

New changes always go through a migration file: `npx supabase migration new <name>`, write the SQL, then `npx supabase db push`. Never edit the remote database by hand (Supabase Studio / SQL editor) without capturing the change back with `npx supabase db pull` into a new migration.

## Promoting the first admin

After the 2026-08-16 security hardening, `is_admin()` trusts only `app_metadata.role` (server-set) or `profiles.role` (trigger-protected). To promote a user, run as the postgres role (Supabase Studio SQL editor or service role):

```sql
update auth.users
set raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb
where email = '<admin email>';
```
